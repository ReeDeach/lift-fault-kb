# lift-fault-kb

[![CI](https://github.com/ReeDeach/lift-fault-kb/actions/workflows/ci.yml/badge.svg)](https://github.com/ReeDeach/lift-fault-kb/actions/workflows/ci.yml)

База знаний по неисправностям лифтов: поиск по коду, полнотекстовый поиск по описанию симптомов и ИИ-диагностика с проверкой по базе.

> **Важно.** Проект — справочник. Он не заменяет документацию производителя,
> инструкции по эксплуатации и правила техники безопасности. Лифт — это
> безопасность людей: работы на оборудовании выполняет только обученный и
> допущенный персонал. Ответы ИИ-диагностики носят справочный характер.

## Стек

- PHP 8.3, MySQL 8
- Поиск: Manticore — Sphinx-совместимый движок (SphinxQL)
- Фронтенд: JavaScript, jQuery и CSS без сборщиков
- Docker, Composer, PHPUnit, GitHub Actions
- ИИ: запрос к API языковой модели, ключ в `.env`

## Запуск

```bash
cp .env.example .env        # заполните пароли
docker compose up -d --build
docker compose exec php composer install
curl http://localhost:8080/api/health
```

База данных:

```bash
docker compose exec php php bin/migrate.php migrate   # применить миграции
docker compose exec php php bin/migrate.php seed      # заполнить производителей
docker compose exec php php bin/migrate.php status    # что применено и что ждёт
docker compose exec php php bin/search.php rebuild    # собрать поисковый индекс Manticore
```

Тесты:

```bash
docker compose exec php composer test
```

## Схема данных

```
manufacturers → models ──(model_controllers)── controllers (УЛ, ПЧ)
                  │                                  │
                  └──────────── fault_codes ─────────┘   (код принадлежит модели или устройству)
fault_codes → fault_code_symptoms → symptoms
fault_codes → fault_code_causes → causes
symptoms → (symptom_causes, likelihood 1–5) → causes → (cause_fixes) → fixes → fix_steps
cases — реальные случаи: дата, описание, код, причина, ремонт, результат
```

Коды ошибок привязаны к **устройству управления** (`controllers`), а не к модели
лифта: один и тот же номер в разных вариантах УЛ может значить разное. Например,
код 45 в УЛ ФБИР.484430.013 означает «нет готовности преобразователя частоты», а в
УЛ ФБИР.484440.500 (ручные двери) — «нет импульсов от устройства контроля скорости».
Модель лифта связана со своими устройствами через `model_controllers`.

Миграции лежат в `database/migrations`, сиды в `database/seeds`. Вторичные индексы
добавлены только там, где это подтвердили замеры (см. «Оптимизация»).

В таблице `cases` не храним адреса объектов, номера лифтов, фамилии и телефоны:
только техническое описание случая. Это проверяет тест `testCasesContainNoPersonalData`.
Поле `source` уникально, поэтому сид случаев можно запускать повторно без дублей.

## API (чтение)

Все ответы с данными содержат поле `disclaimer`. Ошибки приходят как
`{"error": {"status": 400, "message": "...", "fields": {"code": "..."}}}`.

| Метод и путь | Что делает |
|---|---|
| `GET /api/health` | проверка живости |
| `GET /api/manufacturers` | производители и число моделей |
| `GET /api/models?manufacturer=mogilevlift` | модели с устройствами управления и числом кодов |
| `GET /api/codes?model=0401К&code=E36` | поиск кода, `model` — id или название, `manufacturer` — slug |
| `GET /api/codes?model=0401К&limit=20&offset=0` | все коды модели постранично |
| `GET /api/codes?...&expand=tree` | то же с деревом: симптомы, причины, ремонты с шагами, случаи |
| `GET /api/codes/{id}` | один код сразу с деревом |

Что стоит знать:

- Код и название модели принимаются и латиницей, и кириллицей: `А0` и `A0`, `0401К` и `0401K` найдут одно и то же.
- Можно передать несколько кодов через пробел или запятую, до пяти: `code=44 C6` вернёт код 44 и подсказку C6. На индикаторе УЛ их пишут вместе, так же они принимаются и в `/api/diagnose`.
- Код без `model` вернёт все варианты: например, `45` встречается в трёх вариантах УЛ с разным смыслом, у каждого в `owner` указано устройство.
- Причины в дереве: сначала названные в руководстве прямо (`direct: true`), затем пришедшие через симптомы с оценкой `likelihood` 1–5.
- У каждого ремонта есть `safety_note`, если это узлы безопасности (тормоз, ограничитель скорости, замки).
- Неизвестный код — пустой список с `total: 0`, неизвестные модель или производитель — 404.

## Поиск

`GET /api/search?q=двери не закрываются` — полнотекстовый поиск по кодам, симптомам,
причинам, ремонтам (вместе с шагами) и случаям через Manticore.

| Параметр | Что значит |
|---|---|
| `q` | текст запроса, до 300 символов |
| `type` | разделы через запятую: `codes,symptoms,causes,fixes,cases` (по умолчанию все) |
| `model`, `manufacturer` | оставить только коды этой модели; симптомы, причины и ремонты общие и остаются |
| `limit`, `offset` | страница, `limit` до 50 |

Как ищет:

- Слова приводятся к словарной форме (`lemmatize_ru_all`): «дверь не закрывается» находит «Двери не закрываются».
- `ё` и `е` не различаются: «лебедка» находит «лебёдка».
- Документ подходит, если в нём есть хотя бы половина слов запроса, а чем больше совпадений и чем они ближе друг к другу, тем выше документ в выдаче.
- Слово с цифрами, набранное кириллицей-двойником (`Е36`, `А0`), ищется как код латиницей. Обозначения с настоящей кириллицей (`МП2`, `1ДШ`) не меняются.
- Операторы языка запросов Manticore из ввода вырезаются: в запрос попадают только буквы и цифры.
- В ответе `title_html` и `snippet_html` — текст с подсветкой `<mark>`. Остальной HTML экранирован, поэтому вставлять его в страницу безопасно.

Индекс — real-time таблица `kb`: админ-API обновляет документ сразу после записи. Если
Manticore недоступен, запись в базу всё равно проходит, а ответ содержит `warning`. Тогда
индекс восстанавливается командой `php bin/search.php rebuild`. Без Manticore
`/api/search` отвечает 503, остальное API работает. Документы, которых уже нет в MySQL,
в выдачу не попадают, даже если индекс отстал.

## API (запись)

Админ-API закрыто токеном: заголовок `Authorization: Bearer <ADMIN_TOKEN>`. Без
`ADMIN_TOKEN` в `.env` (или если он короче 16 символов) админ-API выключено и отвечает 403.

Разделы `{entity}`: `codes`, `symptoms`, `causes`, `fixes`, `cases`.

| Метод и путь | Что делает |
|---|---|
| `GET /api/admin/{entity}?q=&limit=&offset=` | список, `q` — поиск по названию |
| `GET /api/admin/{entity}/{id}` | запись как есть в базе (у ремонта — с шагами) |
| `POST /api/admin/{entity}` | создать, ответ 201 |
| `PATCH /api/admin/{entity}/{id}` | изменить только переданные поля |
| `DELETE /api/admin/{entity}/{id}` | удалить, ответ 204 |
| `PUT /api/admin/codes/{id}/causes/{causeId}` | причина, названная для кода прямо |
| `PUT /api/admin/codes/{id}/symptoms/{symptomId}` | симптом кода |
| `PUT /api/admin/symptoms/{id}/causes/{causeId}` | причина симптома, тело `{"likelihood": 1..5}` (по умолчанию 3) |
| `PUT /api/admin/causes/{id}/fixes/{fixId}` | ремонт для причины |
| `DELETE` по тем же путям связей | убрать связь |

```bash
curl -X POST http://localhost:8080/api/admin/fixes \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"title": "Очистить контакты замка двери шахты",
       "safety_note": "Работы на крыше кабины — только по наряду-допуску",
       "steps": [{"instruction": "Перевести лифт в режим ревизии"},
                 {"instruction": "Очистить контакты", "expected_result": "Цепь замыкается"}]}'
```

Правила проверки:

- Неизвестные поля — ошибка 400, ошибки приходят сразу по всем полям в `error.fields`.
- Код приводится к латинице (`Е36` → `E36`). Владелец кода — ровно одно из `model_id` и `controller_id`.
- Связанные записи (`model_id`, `cause_id` и т. п.) должны существовать.
- Повтор уникального значения (название симптома, код у того же устройства, `source` случая) — 409.
- В описании и заметках случая не принимаются фамилии с инициалами, телефоны, адреса и регистрационные номера лифтов.
- `steps` у ремонта заменяются целиком, номера шагов проставляются по порядку.
- Повторный `PUT` связи не создаёт дубль: 201 для новой связи, 200 для существующей (`likelihood` обновится).

## Оптимизация

На настоящих данных (около сотни кодов) любой запрос быстрый, и `EXPLAIN` ничего не
показывает. Поэтому замеры идут на синтетической базе: 2000 моделей, 60 тысяч кодов,
по 120 тысяч связей код–симптом и код–причина, 50 тысяч случаев.

```bash
docker compose exec php php bin/bench.php --write   # нужен root MySQL: создаёт и удаляет базу lift_kb_bench
```

Скрипт генерирует данные, применяет миграции без `007_indexes.sql`, замеряет сценарии
API, применяет индексы и замеряет снова. `EXPLAIN` снимается с тех SQL-запросов, которые
реально выполнили репозитории: их записывает `App\Bench\RecordingPdo`. Отчёт с
планами лежит в [docs/performance.md](docs/performance.md).

Что нашли и что сделали (медиана, мс):

| Сценарий | Было | Стало | Что помогло |
|---|---:|---:|---|
| `GET /api/models` (2000 моделей) | 99 569 | 36 | переписан подсчёт кодов |
| `GET /api/models?manufacturer=…` | 5 023 | 3 | переписан подсчёт кодов |
| `GET /api/codes?model=…` | 31 | 3.5 | устройства модели подставляются списком |
| `GET /api/codes?model=…&code=45` | 31 | 3 | то же |
| `GET /api/codes?code=45` | 25 | 2.4 | индекс `idx_fault_codes_code` |

- **Подсчёт кодов у моделей.** Для каждой модели выполнялся подзапрос
  `fc.model_id = mo.id OR fc.controller_id IN (SELECT …)`. Из-за `OR` с подзапросом
  MySQL на каждой модели читал всю таблицу кодов (`type: ALL`, 58 тысяч строк).
  Теперь это два запроса с `GROUP BY` по уникальным ключам, а сумма считается в PHP.
- **Коды модели.** То же `OR` с подзапросом давало полный просмотр. Теперь id устройств
  выбираются заранее и подставляются списком, и MySQL объединяет два уникальных ключа
  (`index_merge`, `sort_union`): читает около 210 строк вместо 58 тысяч.
- **Код без модели.** Уникальные ключи `(model_id, code)` и `(controller_id, code)`
  начинаются с владельца, поэтому для поиска только по коду не годятся. Добавлен
  индекс по `code`.
- **Не добавлено.** Пробовали индекс `cases (fault_code_id, occurred_on)`: случаи
  выбираются сразу для многих кодов и сортируются общим списком, так что сортировку
  он не убрал. Индекс не дал выигрыша и только замедлял бы запись, поэтому его нет.
  Связи между кодами, симптомами и причинами уже обслуживают первичные ключи.

## ИИ-диагностика

`POST /api/diagnose` — разбор неисправности по описанию, коду и модели лифта.

```bash
curl -X POST http://localhost:8080/api/diagnose -H 'Content-Type: application/json'   -d '{"description": "Лифт стоит, на индикаторе 45, пускатель щёлкает", "model": "0401К", "code": "45"}'
```

| Поле | Что значит |
|---|---|
| `description` | описание неисправности, от 10 до 2000 символов (обязательно) |
| `code` | код на индикаторе, можно кириллицей (`Е36`) или несколько через пробел (`44 C6`) |
| `model`, `manufacturer` | модель лифта или производитель: сужают коды и поиск |

Главное правило — **ИИ не придумывает причин, а выбирает их из базы**:

1. Из базы собираются причины-кандидаты (не больше 15). Источники: дерево названного кода
   (причины из руководства и причины через симптомы) и полнотекстовый поиск по описанию
   (похожие симптомы и их причины). У каждого кандидата есть основания, например «Код 45:
   причина названа в руководстве» или «Описание похоже на симптом …, вероятность 4 из 5».
2. Модель получает обращение и кандидатов с их `cause_id` и отвечает строгим JSON по схеме:
   до пяти причин по убыванию вероятности, уверенность, объяснение, что проверить первым,
   и уточняющие вопросы.
3. Ответ проверяется. Причины с `cause_id` не из списка отбрасываются (их число — в
   `ai.discarded`), длинные тексты обрезаются. Названия причин, ремонты, шаги и
   предупреждения по технике безопасности (`safety`) берутся из базы, а не из текста модели.
4. Текст обращения передаётся модели как значение поля JSON, а инструкция прямо говорит,
   что это данные, а не команды. Даже если модель всё же «послушается» пользователя,
   выдуманная причина не пройдёт проверку из пункта 3.

Поле `ai.status` в ответе:

| Статус | Что произошло | Что в `causes` |
|---|---|---|
| `ok` | модель выбрала причины | выбор модели с `confidence`, `reasoning`, `first_check` |
| `rejected` | модель не выбрала ни одной причины из списка | причины из базы по весу, без ИИ |
| `unavailable` | модель недоступна или ответила не по формату | причины из базы по весу, без ИИ |
| `disabled` | не задан `AI_API_KEY` | причины из базы по весу, без ИИ |
| `skipped` | в базе нет подходящих записей, модель не вызывалась | пусто |

Модели и запасные задаются в `.env` (`AI_MODEL`, `AI_FALLBACK_MODELS`). Если основная
модель перегружена (429, 5xx), не отвечает за `AI_TIMEOUT` секунд или снята с публикации
(404), запрос уходит следующей. На «перегружена» (503) та же модель сначала повторяется,
все попытки укладываются в `AI_BUDGET` секунд (35). Сбойная модель ставится на паузу:
после 503 на минуту, без ответа на 15 минут, при исчерпанном лимите (429) до сброса квоты.
Если на паузе все модели, диагностика сразу отвечает причинами из базы. У бесплатного ключа
Gemini лимит около 20 запросов в сутки на модель: для показа в зале этого мало, нужен
платный тариф (оплата за запросы, можно поставить предел трат) или несколько моделей. Ключ передаётся в заголовке `X-goog-api-key` и в URL не попадает.

Без Manticore диагностика работает только по коду (`search: "unavailable"`). В тестах
модель подменена: настоящий API в CI не вызывается, и ключ там не нужен.

## Личный журнал механика

Механик ведёт журнал по своим лифтам: адрес, номер лифта на адресе, что было, что сделано.
Мастер (начальник) видит журналы всех механиков с разбивкой по механикам и общую базу
обезличенных случаев.

**Вход.** Сайт открывается только через Tailscale (`tailscale serve`), а пользователя
сервер узнаёт по заголовку `Tailscale-User-Login`. Пароли не нужны. Чтобы заголовок нельзя
было подделать, nginx слушает только `127.0.0.1`. На стартовом экране две кнопки: «Войти как
механик» (при первом входе механик выбирает себя в списке, и аккаунт привязывается) и «Войти
как мастер» (права мастера только у аккаунтов из `MASTER_LOGINS` в `.env`).

**Запись из ИИ-диагностики.** Под перепиской нажмите «В журнал», выберите механика, адрес
(поиск по первым буквам) и номер лифта. Черновик записи соберётся из переписки сам:
- суть, коды, что было, причина, что дальше и итог;
- «Что сделано» заполняется только из слов механика, ничего не додумывается;
- причина без подтверждения механиком помечается «Предположительно»;
- коды берутся только из переписки.

Без ИИ черновик собирается по шаблону. Механик проверяет его и нажимает «Сохранить».

**Права.** Механик видит записи по своим лифтам и свои собственные (подмена на чужом лифте),
мастер видит всё. Удалить запись может автор или мастер. В Gemini уходит только текст
переписки, без адресов.

**Списки лифтов** — рабочие данные бригады (адреса и фамилии), в репозиторий они не входят.
Файл кладётся в `private/` (папка в `.gitignore`) и загружается командой:

```bash
docker compose exec php php bin/import-lifts.php private/lifts.csv
```

Формат CSV через `;`: `механик;адрес;объект;лифтов;примечание`. На каждый адрес создаются
лифты №1..N. Повторный запуск ничего не дублирует.

**Карточки лифтов** (выгрузка по маршрутам механиков, файлы Word .doc) точнее CSV: на каждый
лифт — номер как в 1С, модель, подъезд, этажность, заказчик. По номеру заявки из отчёта 1С
находят лифт сразу, без сопоставления по адресу (в 1С «2508н», в карточке «2508» — одно и то же).
Сначала карточки разбираются в JSON (только стандартный Python, файл не открывается в Word),
потом загружаются; `--dry-run` показывает, что изменится, ничего не записывая:

```bash
python bin/lift-cards.py private/brigade/*.doc > private/brigade/cards.json
docker compose exec php php bin/import-cards.php private/brigade/cards.json --substitute --dry-run
```

Лифты, которые уже есть в базе, дополняются (по номеру 1С, затем по адресу, затем по дому,
записанному иначе), на них остаются записи журнала и заявки. Лифты механика, которых нет
в карточках, удаляются, если на них ничего не ссылается. `--substitute` — для файла замещения
(под заголовком маршрута подзаголовки других механиков): лифты закрепляются за замещающими.

| Метод и путь | Что делает |
|---|---|
| `GET /api/me`, `POST /api/me/link` | кто вошёл, привязка аккаунта к механику |
| `GET /api/mechanics`, `GET /api/lifts?mechanic_id=` | механики и лифты по адресам |
| `POST /api/journal/draft` | черновик записи из переписки с ИИ |
| `GET /api/journal?lift_id=&mechanic_id=&q=`, `POST /api/journal`, `DELETE /api/journal/{id}` | записи с повторами за 90 дней |

## Заявки на ремонт из отчёта 1С

Заявки на ремонт ведутся в 1С, и каждое утро мастеру на почту приходит отчёт за сутки (XLSX):
номер лифта, адрес, этаж, время заявки и окончания ремонта, «Лифт в ост.», остановок за 30 дней
и «Информация о неисправности». Мастер загружает файл кнопкой «Загрузить отчёт 1С» в разделе
«Заявки → Ремонт · 1С».

- Столбцы ищутся по заголовкам. Коды берутся из «Информации»: «45 MLM;44 C0 MLM» → 45, 44, C0
  («MLM» — приписка диспетчеров, отбрасывается), остальное остаётся текстом («АПСиПДЗ сброс» —
  сработала пожарная сигнализация, ошибка сброшена). «ТО2», «ВнТО» — плановые работы, не вызовы.
- Лифт находится по номеру из 1С (`lifts.reg_number`). Если номера ещё нет, а по адресу в списках
  один лифт без номера, номер запоминается сам. Если лифтов несколько, мастер один раз выбирает
  нужный, и дальше заявки с этим номером сопоставляются сами.
- Механик видит заявки по своим лифтам. Кнопка «Закрыть записью в журнал» открывает запись,
  где уже подставлены лифт, коды, время и пометки 1С.
- Повторная загрузка того же отчёта ничего не дублирует.

| Метод и путь | Что делает |
|---|---|
| `POST /api/repairs/import` | отчёт `{name, data: base64 XLSX}`, только мастер |
| `GET /api/repairs?as=master&report=` | заявки отчёта (по умолчанию последнего) и список отчётов |
| `POST /api/repairs/{id}/lift` | мастер указывает лифт заявки `{lift_id}` |
| `POST /api/repairs/{id}/journal` | заявка закрыта записью журнала `{entry_id}` |

Сами отчёты — рабочие данные (адреса), в репозиторий не попадают: для проверки их кладут в `private/`.

## Заявки на запчасти и общий чат

**Заявки.** Механик пишет, что нужно, сколько, на какой лифт, срочно ли, и прикладывает до
4 фото (деталь, шильдик). Мастер видит заявки всех механиков, отвечает в переписке заявки и
меняет статус: новая → принята → заказана → пришла → выдана (или отклонена). Механик видит
только свои заявки. Когда деталь пришла, он отмечает «Получил деталь».

**Чат.** Один общий чат для механиков всех участков и мастера: вопросы по неисправностям,
поиск детали, кто рядом. У сообщения подписаны механик и его участок. Новые сообщения
подтягиваются раз в 4 секунды. Если в чате или заявках есть новое, на вкладке горит точка.

**Фото.** Телефон сам уменьшает снимок до 1600 точек по стороне и отправляет JPEG. Сервер
принимает только JPEG и PNG до 3 МБ, сверяет тип по содержимому и вырезает метаданные
(EXIF с координатами съёмки). Файлы лежат в томе `uploads`, вне папки проекта. Отдаются через
API с проверкой прав: фото из чата видят все, фото из заявки — её автор и мастер.

| Метод и путь | Что делает |
|---|---|
| `POST /api/uploads` | фото `{data: "data:image/jpeg;base64,…"}`, до отправки сообщения |
| `GET /api/files/{token}` | фото |
| `GET /api/chat?after=&before=`, `POST /api/chat` | общий чат: `{body, photos, as}` |
| `GET /api/requests?as=master&open=1`, `POST /api/requests` | заявки: `{title, quantity, urgent, lift_id, body, photos}` |
| `GET /api/requests/{id}`, `POST /api/requests/{id}/messages` | переписка по заявке, смена статуса `{body, photos, status, as}` |
| `GET /api/updates` | для точки «есть новое» на вкладках |

`"as": "master"` — написать от имени мастера (только для аккаунтов из `MASTER_LOGINS`).

## Push-уведомления

Приходят на телефон, даже когда приложение закрыто. Включаются колокольчиком в шапке, отдельно
на каждом устройстве, в той роли, в которой открыто приложение:

| Кому | О чём |
|---|---|
| механику | новые вызовы по его лифтам из отчёта 1С (повторная загрузка того же отчёта не будит); ответ мастера и смена статуса его заявки на запчасти |
| мастеру | новая заявка на запчасти (срочная — с высоким приоритетом); ответ механика и «деталь получена» |
| всем | сообщения общего чата |

О своих сообщениях не сообщается. «Тишина ночью» — с 22:00 до 7:00 (`APP_TIMEZONE`) ничего не
приходит. Кнопка «Проверить» шлёт пробное уведомление на это устройство.

**iPhone:** уведомления работают только у приложения, добавленного на экран «Домой»
(Safari → «Поделиться» → «На экран Домой»), iOS 16.4 и новее. **Android и компьютер:** Chrome,
Firefox, Edge — прямо из браузера. Нужен HTTPS: через Tailscale (`*.ts.net`) или туннель демо.

**Как устроено.** Стандарт Web Push без сторонних библиотек: текст шифруется ключами браузера
(RFC 8291, проверено по примеру из RFC), сервер подписывается ключами VAPID (RFC 8292).
Уведомления уходят после ответа браузеру, параллельно; подписки, которых больше нет у службы
уведомлений (ответ 404/410), удаляются. Принимаются адреса только служб Google, Mozilla, Apple
и Microsoft — сервер не станет слать запросы на произвольные адреса. Service worker
(`public/sw.js`) ничего не кеширует, только показывает уведомления и открывает нужный экран.

Ключи создаются один раз и вписываются в `.env` (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`,
`VAPID_SUBJECT` — адрес сайта). Без ключей уведомления выключены, остальное работает:

```bash
docker compose exec php php bin/push-keys.php
```

| Метод и путь | Что делает |
|---|---|
| `GET /api/push` | включены ли уведомления, открытый ключ сервера |
| `POST /api/push/subscribe` | `{subscription, role, prefs: {chat, requests, repairs, quiet}}` — подписать устройство или сохранить настройки |
| `POST /api/push/unsubscribe` | `{endpoint}` |
| `POST /api/push/test` | `{endpoint}` — пробное уведомление |

## Демо-версия для показа

Отдельная копия с вымышленными данными: вход без аккаунта (любая роль), плашка «Демо-версия»,
лимит ИИ 15 запросов в час на посетителя и 300 в сутки. Рабочая база и пароли в неё не попадают.

```bash
docker compose -f docker-compose.demo.yml --env-file .env.demo up -d --build
docker compose -f docker-compose.demo.yml --env-file .env.demo exec php php bin/migrate.php migrate
docker compose -f docker-compose.demo.yml --env-file .env.demo exec php php bin/migrate.php seed
docker compose -f docker-compose.demo.yml --env-file .env.demo exec php php bin/demo-reset.php
docker compose -f docker-compose.demo.yml --env-file .env.demo exec php php bin/search.php rebuild
```

Ссылка для зала — бесплатный туннель Cloudflare (адрес случайный и меняется при перезапуске):

```bash
docker run -d --name lift-demo-tunnel --network lift-demo_default cloudflare/cloudflared:latest tunnel --no-autoupdate --url http://nginx:80
docker logs lift-demo-tunnel 2>&1 | grep trycloudflare.com
```

После показа: `docker rm -f lift-demo-tunnel` закрывает ссылку, `bin/demo-reset.php` возвращает демо-данные
(журнал, чат, заявки) и удаляет загруженные фото.

У части провайдеров (например, МТС в Беларуси) домен `trycloudflare.com` заблокирован. Тогда
постоянная ссылка — бесплатный статический домен ngrok (`*.ngrok-free.dev`). Токен и домен из
кабинета dashboard.ngrok.com записываются в `.env.demo` (`NGROK_AUTHTOKEN`, `NGROK_DOMAIN`),
туннель — отдельный контейнер демо, перезапускается вместе с Docker:

```bash
docker compose -f docker-compose.demo.yml --env-file .env.demo --profile tunnel up -d ngrok
```

При первом заходе ngrok показывает гостю страницу-предупреждение: нужно нажать «Visit Site».
Закрыть ссылку: `docker compose -f docker-compose.demo.yml --env-file .env.demo --profile tunnel stop ngrok`.

## Интерфейс

Открывается по адресу `http://localhost:8080/`. Это одна страница на jQuery 3.7.1
(лежит в `public/assets/vendor/`, без CDN и сборщиков): `public/index.html`
и `public/assets/js/app.js`. Экраны переключаются по адресу после `#`.

| Адрес | Экран |
|---|---|
| `#/codes` | поиск кода с выбором модели, список кодов по устройствам |
| `#/codes?code=45` | один вариант — сразу карточка кода; несколько — выбор устройства; ничего — экран «код не найден» |
| `#/codes?code=44 C6` | несколько разных кодов сразу (код и подсказка) — карточки подряд, случаи и симптомы общие |
| `#/codes?id=137` | карточка кода: причины (по РЭ или с оценкой вероятности), ремонты с шагами, симптомы, случаи |
| `#/journal` | личный журнал механика; у мастера — журналы всех механиков |
| `#/base` | общая база обезличенных случаев (мастер) |
| `#/ai` | ИИ-диагностика в виде переписки (поиск по описанию тоже здесь: отдельного экрана поиска нет, `#/search` ведёт сюда): описание, код, модель; ответ с причинами из базы, ремонтами, предупреждениями ТБ и вопросами |

Журнал собирается из дерева кодов (`/api/codes?expand=tree`), поэтому в нём только
случаи, привязанные к кодам, и не больше пяти последних на код.

### Стили

Стили интерфейса перенесены из дизайн-системы Lift Fault Terminal: тёмный терминал,
оранжевый каркас из волосяных линий, широкий гротеск и пиксельные коды. Сборщик не
нужен, nginx отдаёт файлы из `public/` напрямую.

| Файл | Что внутри |
|---|---|
| `public/assets/css/tokens.css` | цвета, отступы, радиусы, шрифты и текстовые стили `.t-…` |
| `public/assets/css/app.css` | компоненты `lft-…` (кнопки, карточка кода, шаги, окно, бейджи, иконки) и каркас экранов `fp-…`, `jr-…`, `ch-…`, `nf-…`, `mb-…` |
| `public/assets/icons/*.svg` | 20 пиксельных иконок 24px, цвет задаётся классом `lft-icon lft-icon--<имя>` |
| `public/assets/img/*.svg` | логотип: знак и надпись |
| `public/styleguide.html` | витрина всех стилей: `http://localhost:8080/styleguide.html` |

Ресурсы подключаются без номера версии, поэтому nginx отдаёт `index.html` и `/assets`
с `Cache-Control: no-cache`: браузер перепроверяет их по ETag, и правки сразу доходят
до телефона.

Шрифты Unbounded, Golos Text, IBM Plex Mono и Jersey 10 подключаются из Google Fonts.
У Jersey 10 нет кириллицы, им набираются только коды и числа. Уже 1024px каркас
складывается в одну колонку.

## Данные

Записи составлены своими словами. Первичный набор для Могилёвлифтмаш
(модели 0401К и ПВБ1010Г) пересказан по разделам «Перечень возможных
неисправностей» руководств по эксплуатации производителя. Коды ошибок УЛ
(77 кодов варианта ФБИР.484430.013, отличающиеся коды трёх других вариантов)
пересказаны по приложениям Д руководств на устройство УЛ, код E36 — по таблице
ошибок ПЧ Hpmont HD5L. Привод дверей кабины с устройством УПДКЛ-2.0 пересказан по
руководствам ДК.00.00.001 РЭ (таблица 7) и ШПЖИ3.105.008 РЭ. Его связь с кодами УЛ 49 и 50
выведена по сигналам ВКО и ВКЗ, которые УПДКЛ выдаёт в УЛ, и это отмечено в описании причин.
Для Doppler Traction MRL ECO II VVVF внесены неисправности 01-32 контроллера E-type
с причинами (раздел 2.4 руководства на E-type). Руководство переведено машинно, термины
приведены к привычным, причины только для гидравлических лифтов не внесены. Однозначный
код (`5`) находит и двузначный (`05`), как он показан на табло E-type.
Источник каждой записи указан в поле `source`.
В описаниях УЛ другие варианты внесены не полностью: что именно, указано в поле
`notes` устройства. Реальные случаи (`cases`) — 23 обезличенные записи из диспетчерского
журнала за сентябрь 2026: из 68 записей выбраны самые информативные (с кодом,
причиной или действием техника), повторы сведены в одну запись с числом повторов
в `notes`. Остальные записи вносятся по практике автора.

Сами руководства и таблицы производителей в репозиторий не включаются:
они защищены авторским правом. Если хотите держать их рядом, положите в
папку `Документация/`, она добавлена в `.gitignore`.
